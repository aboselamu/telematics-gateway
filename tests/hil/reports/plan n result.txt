uint8_t i2c_read(void) {
    // 0. Manager forces a known starting state BEFORE doing anything
    I2C1->CR1 |= (1 << 10);  // SET the ACK bit (Expect to receive)
    
    // 1. Initiate transfer (Manager delegates to Worker)
    i2c_start();
    i2c_send_address(0xD1); // Stops and waits at ADDR flag
    
    // 2. The Smart Manager makes decisions BEFORE opening the floodgates
    I2C1->CR1 &= ~(1 << 10); // CLEAR the ACK bit (Pre-NACK the upcoming byte)
    
    // 3. Manager opens the floodgate
    i2c_clear_addr(); 
    
    // 4. Manager immediately queues the STOP condition
    i2c_stop();
    
    // 5. Worker waits for the hardware to finish clocking the data
    while (!(I2C1->SR1 & (1 << 6))); // Wait for RXNE flag (Bit 6)
    
    // 6. Worker retrieves the final payload
    uint8_t r_data = I2C1->DR;
    
    return r_data;

"The Hardware Reality: The ADDR Floodgate
In the STM32 I2C peripheral, the ADDR flag doesn't just mean "the address matched." It acts as a clock-stretching pause button. While the ADDR flag is set, the SCL line is held LOW by the STM32, pausing the bus so your software has time to decide what to do next.

The moment you clear the ADDR flag (by reading SR1 then SR2), you release the SCL line. The floodgate opens, and the hardware immediately begins clocking in the data bits from the DS3231.

If your i2c_write_address() function automatically clears ADDR before returning, the bus is already clocking in data before your i2c_read() function gets a chance to turn off the ACK bit. You are instantly thrown back into the exact race condition you are trying to write a LinkedIn post about!"
