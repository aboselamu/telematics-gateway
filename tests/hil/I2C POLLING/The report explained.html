Building and Hardware-Verifying a Bare-Metal I²C Driver on the STM32F446RE

From repeated-START transactions and length-specific receive sequences to stuck-bus recovery, fault injection, and 10,000 consecutive hardware transfers

Suggested cover caption:

Hardware setup used to develop and verify the polling-based I²C driver: STM32F446RE, DS3231 RTC, ST-Link debugging, and controlled SDA fault injection.

Reading a few bytes from an I²C peripheral is not difficult when everything is working.

The more important engineering question is:

What happens when the target does not acknowledge, the bus remains busy, SDA is physically held low, a caller passes an invalid pointer, or one transaction fails immediately before another begins?

As part of a larger STM32-based telematics gateway project, I developed a polling-based I²C driver from scratch for the STM32F446RE using direct CMSIS register access.

The objective was not simply to retrieve the time from a DS3231 real-time clock. The objective was to establish a known-good peripheral-driver baseline with:

  • Explicit state management
  • Predictable error classification
  • Correct handling of one-, two-, and multi-byte receives
  • Combined write–read transactions using repeated START
  • Recoverable and non-recoverable fault paths
  • Runtime peripheral recovery
  • Defensive API validation
  • Repeatable hardware verification

The completed implementation passed nine hardware tests, including a controlled stuck-SDA fault and 10,000 consecutive combined transactions with zero failures.

This article describes the driver architecture, the STM32-specific receive sequencing, the verification approach, the failures injected into the physical bus, and the lessons that will carry into the next interrupt-driven version.

1. Project context: an I²C foundation for a telematics gateway

A telematics gateway typically sits between several devices and communication interfaces. Depending on the final architecture, it may interact with:

  • A real-time clock
  • GNSS receivers
  • Cellular modems
  • CAN networks
  • External non-volatile memory
  • Sensors
  • Diagnostic services
  • Local or cloud-facing communication layers

Before building those higher-level services, I wanted a reliable peripheral layer.

The first target was the DS3231 RTC because it provides a simple but useful hardware test case:

  • It uses a standard 7-bit I²C address
  • It supports register-based reads and writes
  • Reading time requires a combined write–read transaction
  • The returned values change continuously
  • The register map provides practical tests for one-, two-, and multi-byte reception

The hardware configuration was:

The driver configures PB6 and PB7 as open-drain alternate-function pins and relies on external pull-ups provided by the I²C hardware setup. The configuration, public API, explicit state enumeration, and detailed error codes are defined in the driver interface.

2. Why I started with a polling implementation

The final gateway will not use a blocking polling driver for every communication operation.

However, beginning with a polling version had important advantages:

  • Every peripheral event could be inspected in sequence.
  • Register transitions could be correlated directly with the reference-manual flow.
  • Error handling could be developed without interrupt concurrency.
  • One-, two-, and N-byte receive behaviour could be verified independently.
  • The completed version could become a reference model for the interrupt-driven implementation.

The V1 contract was intentionally limited:

  • Single execution context
  • Blocking operation
  • Not reentrant
  • Not callable from an interrupt service routine
  • One active transaction at a time

That limitation was deliberate. The aim was correctness and observability before concurrency.

The current timeout is also implemented as a software loop counter. This is sufficient for bring-up and controlled testing, but the real elapsed timeout depends on CPU frequency, compiler optimisation, and register-access latency. A later version should replace it with a timer- or system-tick-based deadline.

3. Public driver interface

The driver exposes six primary functions:

i2c_status_t i2c_init( 
   const i2c_config_t *p_config); 
 
i2c_status_t i2c_write( 
   uint8_t device_address, 
   const uint8_t *p_data, 
   uint16_t length); 
 
i2c_status_t i2c_read( 
   uint8_t device_address, 
   uint8_t *p_data, 
   uint16_t length); 
 
i2c_status_t i2c_write_read( 
   uint8_t device_address, 
   const uint8_t *p_tx_data, 
   uint16_t tx_length, 
   uint8_t *p_rx_data, 
   uint16_t rx_length); 
 
i2c_state_t i2c_get_state(void); 
 
i2c_status_t i2c_recover(void);

The interface separates four responsibilities:

  • Initialization
  • Standalone transmission
  • Standalone reception
  • Combined write–read operation

The combined function is particularly important for register-based peripherals.

To read the DS3231 seconds and minutes registers, for example, the controller must:

START
→ address + write
→ transmit register address 0x00
→ repeated START
→ address + read
→ receive requested bytes
→ NACK final byte
→ STOP

Generating a STOP between the write and read phases would create two independent transactions and would not preserve the intended register-access sequence.

4. Explicit driver states

One design decision that improved both testing and fault handling was to make the software state explicit.

typedef enum 
{ 
   I2C_STATE_RESET = 0, 
   I2C_STATE_READY, 
   I2C_STATE_BUSY_TX, 
   I2C_STATE_BUSY_RX, 
   I2C_STATE_BUSY_TX_RX, 
   I2C_STATE_ERROR 
} i2c_state_t;

The state model establishes a clear contract:

RESET
|
| successful initialization
v
READY
|
| transaction admitted
v
BUSY_TX / BUSY_RX / BUSY_TX_RX
|
| clean STOP and completion
v
READY

A hard failure follows a different path:

BUSY
|
| timeout, unusable bus or uncertain peripheral state
v
ERROR
|
| explicit successful recovery
v
READY

This prevents the application from beginning a new operation when the physical or peripheral state is uncertain.

For example:

  • Calling a transaction before initialization returns I2C_ERR_NOT_INIT
  • Calling while another operation is active returns I2C_ERR_BUSY
  • Calling after a hard failure returns I2C_ERR_LOCKED
  • Invalid addresses, lengths, or pointers return I2C_ERR_PARAM
  • A detected unusable bus returns I2C_ERR_BUS

The full set of status and state values is part of the public driver interface.

5. Software state and physical bus state are not the same thing

A key lesson from this work was that software state alone is insufficient.

The driver may believe it is READY, while the peripheral’s SR2.BUSY flag indicates that the physical bus is still occupied or stuck.

For this reason, transaction admission includes two checks:

  1. Is the software state READY?
  2. Is the hardware bus actually idle?

A simplified form of the gatekeeping logic is:

switch (s_state) 
{ 
   case I2C_STATE_READY: 
       if ((I2C1->SR2 & I2C_SR2_BUSY) != 0U) 
       { 
           s_state = I2C_STATE_ERROR; 
           return I2C_ERR_BUS; 
       } 
 
       s_state = I2C_STATE_BUSY_TX_RX; 
       break; 
 
   case I2C_STATE_RESET: 
       return I2C_ERR_NOT_INIT; 
 
   case I2C_STATE_BUSY_TX: 
   case I2C_STATE_BUSY_RX: 
   case I2C_STATE_BUSY_TX_RX: 
       return I2C_ERR_BUSY; 
 
   case I2C_STATE_ERROR: 
       return I2C_ERR_LOCKED; 
 
   default: 
       return I2C_ERR_LOCKED; 
}

This protects the driver from starting a new transaction merely because an internal variable says the controller is available.

The implemented transaction managers validate parameters, check both the software and hardware states, acquire the correct busy state, execute the transfer, verify STOP completion, and only then return to READY.

6. The STM32 receive problem: one size does not fit all

One of the most important technical parts of the driver was the receive implementation.

On this STM32 I²C peripheral, a one-byte receive, a two-byte receive, and a longer receive cannot be handled with one generic loop.

The sequence in which software modifies ACK, POS, clears ADDR, requests STOP, and reads the data register affects what the peripheral places on the bus.

The driver therefore uses three dedicated receive helpers:

i2c_receive_1_byte(...); 
i2c_receive_2_bytes(...); 
i2c_receive_n_bytes(...);

The public i2c_read() and i2c_write_read() functions dispatch according to the requested receive length.

6.1 One-byte receive

For a single-byte read, the controller must prepare to NACK the first and only byte.

The critical ordering is:

Generate START
→ send address in read mode
→ wait for ADDR
→ disable ACK
→ clear ADDR
→ request STOP
→ wait for RXNE
→ read DR

The significant point is that ACK is disabled before clearing ADDR.

Clearing ADDR opens the receive path. If the peripheral remains configured to ACK at that point, the controller may acknowledge a byte that should have been the final byte.

6.2 Two-byte receive

The two-byte case uses a different sequence:

Set POS
→ clear ACK
→ clear ADDR
→ wait for BTF
→ request STOP
→ read first byte
→ read second byte
→ restore normal ACK/POS configuration

Waiting for BTF indicates that the final two bytes are ready in the receive pipeline.

6.3 N-byte receive

For a longer transfer, ACK remains enabled while the intermediate bytes are received.

The sequence changes when three bytes remain:

Receive intermediate bytes normally
→ when three bytes remain, wait for BTF
→ clear ACK
→ read N-2 byte
→ wait for BTF again
→ request STOP
→ read final two bytes

Separating these paths made the code easier to review and made the verification tests much more meaningful.

A generic loop might appear shorter, but it would hide the exact hardware sequencing that determines whether the final bytes are acknowledged correctly.

7. Combined write–read with repeated START

A DS3231 register read begins with a write phase containing the register address.

The transmit helper performs:

START
→ write address
→ clear ADDR
→ send register-address byte
→ wait for final BTF

For a standalone write, the driver requests STOP after the final BTF.

For a combined transaction, it deliberately does not generate STOP.

Instead, while the controller still owns the bus, the selected receive helper generates another START. Because the bus remains owned, that becomes the required repeated START.

The high-level sequence is:

status = i2c_transmit_phase( 
   address, 
   p_tx_data, 
   tx_length); 
 
if (status == I2C_OK) 
{ 
   if (rx_length == 1U) 
   { 
       status = i2c_receive_1_byte( 
           address, 
           p_rx_data); 
   } 
   else if (rx_length == 2U) 
   { 
       status = i2c_receive_2_bytes( 
           address, 
           p_rx_data); 
   } 
   else 
   { 
       status = i2c_receive_n_bytes( 
           address, 
           p_rx_data, 
           rx_length); 
   } 
}

Only after the receive helper has requested STOP does the transaction manager verify that the hardware returned to an idle state and release the software state back to READY.

8. Error classification: not every failure should lock the driver

One of the more useful design distinctions was separating a recoverable target NACK from a failure that leaves the hardware state uncertain.

Recoverable NACK

A NACK can be a legitimate transaction result:

  • No target is connected at the requested address
  • The target is temporarily unavailable
  • The address is wrong
  • The target refuses the current operation

When a NACK occurs, the driver:

  • Requests transaction termination
  • Clears relevant residual control conditions
  • Verifies STOP completion
  • Returns I2C_ERR_NACK
  • Returns the state to READY only when cleanup succeeds

This means the application receives the original NACK result without losing the ability to perform another transaction.

Hard or uncertain failure

Timeouts, bus errors, overruns, arbitration-related failures, or failed cleanup are treated differently.

The driver moves to:

I2C_STATE_ERROR

Further transaction attempts return:

I2C_ERR_LOCKED

The application must explicitly call:

i2c_recover();

This avoids silently continuing after an operation that may have left the peripheral or physical bus in an unknown condition.

The source implements this distinction consistently across read, write, and combined write–read operations.

9. Hardware verification strategy

The driver was verified using:

  • STM32F446RE hardware
  • DS3231 RTC module
  • ST-Link debugging
  • VS Code with Cortex-Debug
  • OpenOCD
  • GDB expressions
  • Direct register inspection
  • Controlled disconnection of SDA
  • Controlled pull-down of SDA through a resistor
  • Repeated hardware transactions

The most useful register and GPIO checks were:

p/x (GPIOB->IDR & 0xC0) 
p/x I2C1->SR1 
p/x I2C1->SR2 
p/x I2C1->CR1

For PB6 and PB7:

0xC0 = 0b11000000
PB7/SDA = high
PB6/SCL = high

During a forced-low SDA fault:

0x40 = 0b01000000
PB7/SDA = low
PB6/SCL = high

The verification was organised into nine tests.

10. Test 1 — Recoverable address NACK during a combined transaction

The first fault test disconnected the DS3231 SDA connection while preserving the line pull-up.

The driver attempted a combined write–read transaction to address 0x68.

The expected result was:

Transfer result: I2C_ERR_NACK
Driver state: I2C_STATE_READY
SCL: high
SDA: high
SR2.BUSY: clear

The important result was not only detecting the NACK.

The driver also completed the STOP/cleanup path and returned to READY, proving that an address NACK did not permanently lock the peripheral.

The combined operation was not the only API path tested.

The application first used i2c_write() to set the DS3231 register pointer to 0x00, and then issued an independent i2c_read().

Both calls completed successfully:

15. Test 6 — NACK handling across separate operations

The SDA connection was disconnected again.

This time the application called:

i2c_write()

followed by:

i2c_read()

Both returned:

I2C_ERR_NACK

After each failed transaction, the driver returned to:

I2C_STATE_READY

This demonstrated that a NACK during one independent operation did not poison the next API call.

16. Test 7 — Runtime recovery from a physically stuck SDA line

This was the most important fault-injection test.

The RTC remained connected normally, but PB7/SDA was temporarily pulled to ground through a resistor.

The complete sequence was:

Normal initialized system
→ force SDA low
→ attempt combined transaction
→ transaction fails
→ driver enters ERROR
→ call recovery while SDA is still low
→ recovery must fail
→ release SDA
→ call recovery again
→ recovery must succeed
→ perform another RTC transaction
→ transaction must succeed

No MCU reset, power cycle, or debugger restart was allowed between the fault and the recovery.

16.1 Fault present

With SDA forced low:

GPIOB->IDR & 0xC0 = 0x40
I2C1->SR2 = 0x02

This represented:

SCL high
SDA low
BUSY asserted

The transfer returned:

I2C_ERR_BUS

The driver entered:

I2C_STATE_ERROR

16.2 Recovery attempted while the fault remained

While SDA was still low:

i2c_recover() → I2C_ERR_BUS

The state remained:

I2C_STATE_ERROR

This was essential. A recovery function must not claim success while the physical reason for the fault still exists.

16.3 Fault released

The temporary SDA-to-ground resistor was removed while the debugger remained attached and the MCU was not reset.

The GPIO input then showed:

GPIOB->IDR & 0xC0 = 0xC0

Both lines were high.

The second recovery attempt returned:

I2C_OK

The state returned to:

I2C_STATE_READY

A subsequent two-byte RTC read also returned:

I2C_OK

The final state remained:

I2C_STATE_READY

This proved the complete runtime path:

Physical fault
→ transaction failure
→ ERROR state
→ failed recovery while fault remains
→ fault removed
→ successful peripheral recovery
→ READY state
→ successful post-recovery transaction

20. What the testing changed in the design

The verification phase did more than confirm the implementation. It sharpened several architectural decisions.

20.1 A NACK should not automatically become a permanent error

A target NACK is often recoverable.

Locking the entire driver after every NACK would make normal device absence or address probing unnecessarily disruptive.

The final implementation distinguishes:

Transaction failed, but cleanup succeeded

from:

Transaction failed, and the bus state is uncertain

That distinction makes the API more useful to the application layer.

20.2 READY must mean both software-ready and hardware-idle

A state variable alone cannot prove that the physical bus is usable.

The driver therefore checks SR2.BUSY when admitting a new operation.

20.3 Recovery must be tested against a physical fault

Calling i2c_recover() on a healthy bus proves very little.

The meaningful test was:

Force SDA low
→ confirm recovery fails
→ release SDA
→ confirm recovery succeeds
→ confirm the next transaction works

20.4 Completion means more than receiving the last byte

A transaction is not complete merely because the final data register was read.

The driver verifies that STOP has completed and the bus has returned to a defined idle condition before it changes the state back to READY.

20.5 Length-specific paths deserve independent tests

A working seven-byte read does not prove a one-byte read, and a working one-byte read does not prove the two-byte POS/BTF sequence.

Each path needed its own hardware test.

21. Current limitations

The polling version is now a useful reference implementation, but it is not the final gateway driver.

Its main limitations are:

Blocking execution

The CPU waits for each I²C hardware event.

This is acceptable for early bring-up and very short transactions, but it does not scale well when the gateway must service multiple peripherals and communication interfaces.

Software-loop timeout

The timeout is based on iteration count rather than an absolute time source.

The next implementation should use a hardware timer or monotonic system tick.

Single execution context

The V1 driver is not reentrant and must not be called from an ISR.

Recovery scope

The current recovery resets and reconfigures the I²C peripheral and verifies that the bus becomes idle.

It does not yet perform a full GPIO-based bus-clear sequence with multiple SCL pulses. Such a sequence may be required when a target device remains internally stuck and continues holding SDA low after the original fault source has been removed.

Single-controller assumptions

The current admission policy interprets an unexpected BUSY condition as a stuck or inconsistent bus.

A genuine multi-controller design would need different arbitration and ownership rules.

Logic-level protocol capture

Register inspection and hardware fault injection formed the main evidence for this phase. A formal logic-analyser capture and decoded timing report can still be added as supplementary protocol-level evidence.

22. The next phase: interrupt-driven I²C

The verified polling implementation will now be frozen as a reference baseline.

The next version will use:

I2C1_EV_IRQHandler(); 
I2C1_ER_IRQHandler();

The application will start an operation and return immediately:

status = i2c_write_read_it( 
   DS3231_I2C_ADDRESS, 
   ®ister_address, 
   1U, 
   rtc_data, 
   2U);

The event interrupt will advance the transaction through stages such as:

START generated
→ address phase
→ transmit bytes
→ repeated START
→ receive bytes
→ STOP
→ completion

The error interrupt will classify:

  • NACK
  • Bus error
  • Arbitration lost
  • Overrun
  • Other peripheral errors

The development order will be:

Interrupt-driven write
→ one-byte read
→ two-byte read
→ N-byte read
→ combined write–read
→ error ISR
→ timer-based timeout supervision
→ runtime recovery
→ regression against the polling-driver tests

DMA is not required for the first interrupt-driven implementation.

The current DS3231 transactions are only a few bytes long. Interrupt-driven operation will remove the blocking behaviour while keeping the transaction state observable.

DMA can be considered later for larger or continuously streamed data, particularly on interfaces such as UART, SPI, external storage, or high-rate sensor acquisition.

23. Closing thoughts

A peripheral driver is not complete when the first valid byte appears in a debugger.

It becomes trustworthy when its behaviour is defined and tested across:

  • Normal operation
  • Boundary-length transfers
  • Repeated transactions
  • Target absence
  • Bus faults
  • Recovery attempts
  • Invalid application requests
  • Post-error operation

The most valuable result from this phase was not that the DS3231 returned the correct seconds value.

It was that the driver demonstrated a repeatable lifecycle:

RESET
→ READY
→ BUSY
→ successful completion
→ READY

and, under a physical fault:

RESET / BUSY
→ ERROR
→ failed recovery while fault remains
→ successful recovery after fault removal
→ READY
→ successful next transaction

That verified polling implementation now provides a stable behavioural reference for the interrupt-driven architecture that follows.
